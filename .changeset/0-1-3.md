## Channels

- **WhatsApp is bundled**, like Telegram. No `plugins add` step — name the channel and it works.
  `dispach init --whatsapp connected --whatsapp-number <digits>`, then `dispach serve`.
- **Pairing is an 8-character code**, not a QR. New `pairWith` field on the channel names the
  account to link; omit it and pairing falls back to a QR.
- **`init` offers the code where the number was typed.** Enter a WhatsApp number at the wizard and
  it connects, shows the code and waits for the phone. Skipped without a terminal, bounded so it
  cannot hang, and it never fails the init — the agent is already written by then.
- `pairWith` is **not** `allowFrom`: the first is the account the agent runs as, the second is who
  may message it. The old wizard question asked for both at once and wrote the answer to `allowFrom`.
- The code is shown by `dispach channels list <agent>`, on the `serve` banner, on
  `GET /v1/agents/:id`, and in the web UI. Previously it reached no command at all.
- **The chat with yourself works.** A freshly paired agent answered nothing: the owner's own
  messages arrive as `fromMe` and were discarded as the agent's echo. The agent's replies are told
  apart by id; the owner's chat by the account's own JID. Same as OpenClaw's `selfChatMode`.
- **Numbers take a `+` and separators everywhere** — `pairWith`, `allowFrom`, the wizard, the
  flag. `+880 1711-223344` is folded to digits; a literal comparison used to match nobody.
- LID-addressed chats report the phone number from `remoteJidAlt`. Under WhatsApp's newer
  addressing the sender was an opaque id that matched no `allowFrom`.
- **The paired account is always admitted.** A channel paired to a number vouches for that
  number; `allowFrom` means who *else*. A fresh pairing used to refuse its own owner until they
  edited the manifest and restarted.
- `dispach channels pair <agent> <channel>` — one verb, the way each channel needs it: a code
  for WhatsApp, a token for Telegram. Shows the running host's code if there is one, pairs on its
  own if not.
- The `serve` banner prints a pairing code inline. It used to point at the API for eight
  characters the terminal already had.
- **A second pairing code was requested mid-login**, on the reconnect WhatsApp demands after the
  phone accepts the first — clobbering the pairing about to finish. The phone showed a linked
  device that never worked. The guard now keys on pair-success (`account`), not on `registered`.
- `dispach channels <agent> [connect | disconnect | credential | unpair]`, and
  `PATCH /v1/agents/:id/channels/:channelId` + `POST …/unpair`. The browser panel was read-only.
- Credentials are write-only; the target variable is resolved from the manifest, never the caller.

**Read this before pairing a number.** Baileys reverse-engineers WhatsApp Web. WhatsApp's terms do
not permit it and a banned number has no appeal. **Use a spare one.** It also does not pair under
Bun — use the npm-installed `dispach` rather than the compiled binary or the container image. The
channel says so at start. Image grew 542 → 551 MB.

## Plugins

- `dispach plugins add | list | remove` — a plugin can be installed.
- Three lookups: built-in registry → `~/.dispach/plugins/` → module import. `list` says which
  answered, and the commit.
- One self-contained bundle. `add` refuses a tree with runtime dependencies and no bundled
  `node_modules`, and runs `conformance()` before writing the manifest entry.
- `--ref` pins a tag or commit. No integrity check — the `dispachApi` gate is compatibility, not
  authenticity.
- **Breaking:** `dispach plugins <agent>` is now `dispach plugins list <agent>`.

## An agent starts if it can take a turn

- A broken channel, plugin, tool provider or pinned tool is a **warning**, not a refusal.
  `init --telegram connected` previously generated an agent that would not start.
- Reported on `agent.warnings`, the `serve` banner, `GET /v1/agents/:id`, a new browser warnings
  panel, and the agent's own configuration block.
- Still fatal: the model block, the schema, workspace files, the rule budget, a duplicate channel `id`.
- `validate` builds the tool registry the way `run` does — the two used to disagree.

## Serving

- **A taken port moves the server** to the next free one and says so, instead of dead-ending.
  An explicit `--port` still refuses, because a flag is an instruction.
- **A failed turn says why.** `POST /messages` answered 200, the stored session stayed empty and
  nothing reached the log. The browser and `serve` now render the `error` event like the CLI does.

## Fixes

- `channels list` said `connected` when it meant `enabled` in the YAML, and `paired by QR` for a
  channel that had never paired. It now reports what the manifest says plus live host status.
- `creds.json` existing is not a pairing — Baileys writes it before linking, with `registered: false`.
- The QR is drawn in the browser instead of printed as 277 characters of base64.
- A channel factory returning no `type` reached the banner as `echo (undefined)`; a transport whose
  `id` or `type` disagrees with its manifest entry is refused at load.
- `serve()` dropped its fifth forwarded option — a supplied capability answered `501`.
- **Every pane command in the compiled binary was broken.** `/channels`, `/skills`, `/config` and
  the rest answered `Unknown command "/$bunfs/root/…"` — the binary is its own command and was
  being passed its own embedded path as the first argument. The generated service definition had
  the same bug, which would have exited 1 at every boot.
- The wizard never asked its own WhatsApp question; only the flag worked.
- `stop()` immediately after `start()` could hang the WhatsApp transport forever.
- A refused pairing reconnected on a 1-second backoff forever — three codes in fifteen seconds,
  each invalidated before it could be typed, and every pass a failed pairing against a real number.
  It now backs off and stops after three.
- The landing palette overflowed a 30-row terminal, scrolling the first command off the top.
- `docs/03-SPEC-PLUGIN-API.md` documented a Channel interface that has never existed.
