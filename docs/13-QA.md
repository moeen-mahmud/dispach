# 13 — QA pass

A tester's pass over a release candidate. It covers two things: nothing that worked in 0.1.3 has
stopped working, and every 0.2.0 surface does what its docs say. Run it before a pilot tag reaches
anyone, and again before a stable tag.

The suite already proves the machinery (about 3,800 tests under Bun, 1,500 under Node, and the
control-plane e2e). This pass covers what the suite cannot reach:

- a store written by the previous release;
- a real terminal;
- a real browser;
- a real bot and a real phone;
- a real Docker host.

**How to use it.** Each case has an ID, which the live tracker mirrors. Record a result against the
ID: pass, fail with the evidence, or a justified deviation. Cases marked ★ are the smoke subset.
Run those first, and stop the area if one fails. Areas are ordered cheapest first.

**Severity** of anything found:

| Sev | Meaning | Rule |
| --- | --- | --- |
| 1 | Data loss, a cross-silo or cross-agent leak, a lost or duplicated delivery | Stops the release |
| 2 | A surface broken for everyone | Fixed before the pilot |
| 3 | Degraded, with a workaround | Tracked |
| 4 | Cosmetic | Tracked |

**Exit:** every case passes or carries a recorded, justified deviation. No Sev-1 or Sev-2 is open.

## Setup

```bash
# Build the candidate once
bun install && bun run build
bun run verify:package                                  # packs, installs into an empty dir, runs it
docker compose build                                    # the runtime image, dispach:local tags
docker compose -f packages/control/compose.yaml build   # the control plane image

# A scratch sandbox. Never test against ~/.dispach
export DISPACH_HOME=$(mktemp -d)/home
export DISPACH_NO_BOOTSTRAP=1       # hand-run cases must not install a LaunchAgent; unset only in C3
```

You need:

- **Model endpoints:** DeepSeek (`MODEL_API_KEY`), plus one other provider for the portability
  cases. Any OpenAI-compatible host serving open weights counts.
- **Telegram:** a throwaway bot token from @BotFather, and a second account to message it from.
- **WhatsApp:** a spare phone number that can be paired.

Evidence is the command plus its real output, or a screenshot for anything visual. Paste it, or link
it, on the tracker.

## A. Upgrade: never break what works

The one area the suite cannot cover, because every test starts from an empty store.

### A1 ★ A 0.1.3 sandbox opens under the candidate

**Before:**

```bash
export DISPACH_HOME=/tmp/qa-013/home
npm i -g dispach@0.1.3
dispach init --yes --user <you> --name Milo --preset deepseek --model deepseek-v4-pro --schedules daily
# put the key in ~/.dispach/agents/milo/.env: init writes an empty MODEL_API_KEY= line, so edit it, never append
dispach run milo --plain --input "Remember this for later: my favourite colour is teal."
dispach serve &           # then `dispach web` and claim the UI once, so a key exists
dispach credential create # mint one operator key and write its secret down
```

**Steps:** install the candidate over it (`npm i -g ./dispach-<version>.tgz`) with the same
`DISPACH_HOME`. Then run `dispach validate`, `dispach schedules`, `dispach sessions`, and
`dispach run --input "what is my favourite colour?"`.

**Expect:**
- Every command exits 0 and nothing asks for re-setup.
- The agent answers "teal".
- The schedule shows the same next run as before.
- The old session is listed with its messages.

**Evidence:** `schedules` before and after, the reply, `sessions`.

### A2 ★ Old credentials still authenticate

**Steps:** `dispach serve` in one terminal. In another:

```bash
curl -s -H "Authorization: Bearer <A1 key>" localhost:7420/v1/agents
```

**Expect:** `200`, the agent listed. A 0.1.3 key has no scope, so it keeps full access.

**Evidence:** the curl output.

### A3 The migrated store carries the 0.2.0 tables and loses nothing

**Steps:** `sqlite3 $DISPACH_HOME/store.db '.tables'`, plus row counts of `messages` and
`schedules` before and after the upgrade.

**Expect:** the counts are unchanged. The usage and webhook tables exist. `GET /v1/usage` reports a
`meteredSince` after the upgrade and counts nothing from before it.

### A4 A 0.1.3 container volume keeps working under the new image

**Steps:**
1. `DISPACH_VERSION=0.1.3 docker compose up -d`.
2. Run `dispach init --yes` inside it (`docker compose exec server dispach init --yes`) and one turn.
3. `docker compose down`, **keeping the volume**, then bring it up again on `DISPACH_VERSION=local`.

**Expect:**
- The same agent comes up with its history.
- `/v1/ready` answers within seconds.
- The pid-1 lease left by the old container does not block the new one.

**Evidence:** `docker compose logs server | head`, and the `/v1/ready` timing.

## B. Install and first run

### B1 ★ The tarball installs and runs on a clean machine

**Steps:** `npm i -g ./dispach-<version>.tgz` in a fresh shell, then `dispach --version` and
`dispach --help`.

**Expect:** the version is the candidate's. The help lists every command. Every flag has at least
one space before its description.

**Regression:** `--telegram-allow <@handle>` used to run into its description.

### B2 ★ `init` wizard, the full-screen path

**Steps:** `dispach init`. Answer every question with something other than the default at least
once over the run.

**Expect:**
- No row wraps at 80 columns.
- ↑ and ↓ skip headings.
- The confirm screen names the directory that is then written.
- The agent lands under `$DISPACH_HOME/agents/<slug>`, never in the cwd.

**Evidence:** a screenshot of the confirm screen, and `ls $DISPACH_HOME/agents`.

### B3 `init --yes` and flags

**Steps:** `dispach init --yes --user <you> --name Tg --telegram connected --telegram-allow @you --system read`.
Separately, run `dispach init milo`.

**Expect:**
- The first writes the flags into `agent.yaml`: check `allowFrom` and the system level.
- The second is refused with a hint pointing at `--dir`.

### B4 ★ `validate`, `workspace`, `tools`

**Steps:** `dispach validate`, `dispach workspace`, `dispach tools` on the B2 agent. Then break the
manifest (`maxSteps: banana`) and run `validate` again.

**Expect:** the first three exit 0. The broken manifest makes `validate` exit 1 and name the field.

### B5 ★ `run`, the chat session

**Steps:** `dispach run`, then:
1. Send a multi-step request that uses a tool.
2. Scroll with PgUp, PgDn, ⌥↑ and ⌥↓.
3. Press `esc`.
4. Paste a 12-line block.
5. Type `/help`, then `/sessions`, then `/restart`.
6. Press `^C` once, wait, then press it twice.

**Expect:**
- The reasoning folds, with ⌥r to open it.
- The tool rows pair with their calls.
- The paste composes rather than sending.
- `/restart` keeps the transcript.
- A single `^C` arms; two exit.
- The status line never takes a second row at 80 or 100 columns.

**Evidence:** screenshots at 80 columns.

### B6 Resume

**Steps:** exit, then `dispach run` again and pick the previous session.

**Expect:** the earlier conversation is painted, not a blank screen under "17 message(s)".

### B7 `--plain` matches a pipe

```bash
dispach run --plain --input hi > a.txt
dispach run --plain --input hi | cat > b.txt
```

**Expect:** apart from the model's own wording, both files have the same structure: banner, reply
and end note. No escape sequences in either (`grep -c $'\x1b' a.txt` prints 0).

### B8 A turn stopped by its budget says so

**Steps:** set `limits.maxSteps: 2` and ask for a task that needs five tool calls.

**Expect:** the end note names `max_steps` in both the TUI and `--plain`. The exit status is
non-zero.

## C. Server and web

### C1 ★ `serve` and the web UI

**Steps:**
1. `dispach serve`, then `dispach web`.
2. Claim the UI in the browser.
3. Chat, open the panels (channels, schedules, approvals, keys), and reload the page mid-reply.

**Expect:**
- The reply continues after the reload, because turns are detached from the connection.
- There are no console errors.

**Evidence:** screenshots, and the console.

### C2 Keys and scopes from the CLI

**Steps:**
1. `dispach credential create --agents <one> --can chat,read`.
2. Use it on `GET /v1/agents`, `POST …/messages` and `GET /v1/events`, each with no `agentId`.
3. Use it on `POST /v1/agents/:id/stop`.

**Expect:**
- `GET /v1/agents` lists only the scoped agent.
- `GET /v1/events` streams only that agent's events.
- `stop` answers `403`.
- Another agent's id answers `404`, byte-identical to an imaginary id.

### C3 `daemon install`, `status`, `stop`, `start`

**Steps:** unset `DISPACH_NO_BOOTSTRAP`, then:
1. `dispach daemon install`, then `dispach daemon status`.
2. `dispach stop <agent>`, then `status`.
3. `dispach start <agent>`.
4. Log out of macOS and back in.
5. `dispach daemon uninstall`.

**Expect:**
- `status` exits 0 while running.
- A stopped agent is named along with the command that reverses it.
- The service comes back after the login.
- Nothing is left in `launchctl print-disabled gui/$UID` for the label.

### C4 The WebSocket and `run` attaching to a live host

**Steps:** with `serve` up, run `dispach run` in another terminal.

**Expect:**
- It attaches rather than building a second runtime: `/status` says attached.
- A cancel mid-turn stops the turn on the host.
- The web UI shows the same turn live.

### C5 In the container

**Steps:** `docker compose up -d`, then:
- `docker compose exec server dispach status`
- `docker compose exec server dispach web url`

**Expect:**
- `status` reads "running · pid 1", with the note "a serve process, not an installed service".
  **Regression:** it used to say "running in a terminal".
- `web url` prints a clickable host, not `0.0.0.0`.

## D. Channels

### D1 ★ Telegram, long-poll

**Steps:** put the bot token in the agent's `.env` and `allowFrom: [@you]`. Run `dispach serve`,
then message the bot from your account.

**Expect:** a reply within a few seconds. `status` shows the channel connected.

**Evidence:** a phone screenshot, and `status`.

### D2 Telegram refuses a stranger clearly

**Steps:** message the bot from the second account.

**Expect:**
- No reply to the stranger.
- The `serve` stdout (not stderr) names the sender and the exact `allowFrom` line to add.
- `status` lists it under attention.

### D3 ★ WhatsApp pairing through the web UI

**Steps:** add a WhatsApp channel, `serve`, then open the channel panel.

**Expect:**
- The QR renders and rotates about every 20 s, with its issue time visible.
- Scanning it pairs the phone.
- A message from the allowed number gets a reply.

### D4 WhatsApp pairing through the API

**Steps:** `GET /v1/agents/:id` during pairing.

**Expect:** `channels[].status` is `needs_input`, and `channels[].input` carries
`{kind, payload, issuedAt}`. A client can render the QR from that payload alone.

### D5 A failed delivery is not reported as ok

**Steps:** schedule a delivery to a Telegram chat id the bot has never seen.

**Expect:** `dispach schedules` shows the failure (`chat not found`), not `ok`.

## E. Tools, skills, memory

### E1 ★ The `exec` policy and the write root

**Steps:** on a `--system full` agent:
- ask it to run `git status`;
- ask it to write a file outside `workspace/`;
- ask it to delete `~`.

**Expect:**
- `git status` runs.
- `file_write` outside the root is refused, naming the root.
- Deleting `~` is refused by the hardline floor, whatever the policy says.

### E2 Web fetch and search

**Steps:**
- ask for a page summary;
- ask it to fetch `http://169.254.169.254/`;
- ask a question that needs search (if a search backend is configured).

**Expect:** the page is summarised, the metadata address is refused, and the search is answered.

### E3 Skills

**Steps:** `dispach skills --help`, then install one catalogue skill and ask for a task that needs it.

**Expect:** the row shows the skill's token count, the skill is selected for the task, and
`skills list` shows its source commit.

### E4 ★ Memory across sessions

**Steps:**
1. "Remember I'm vegetarian."
2. Exit, open a new session.
3. Ask for a dinner idea.

**Expect:** a vegetarian answer, and `MEMORY.md` holds the note.

### E5 Knowledge

**Steps:** add `knowledge/pricing.md` with `keywords: [pricing]`, then ask about pricing.

**Expect:** the answer uses the entry. An unrelated question does not pull it in: check with
`GET /v1/agents/:id/context`.

## F. Schedules

### F1 ★ cron, every, at

**Steps:** declare one of each (`every: 5m`, a cron two minutes out, an `at` three minutes out),
then `serve`.

**Expect:** each fires once at its time. `dispach schedules` shows `ok` and the next run.

### F2 Delivery to Telegram

**Steps:**
1. `dispach schedules --recipients` to find your chat id.
2. Point a schedule's `deliver.to` at it.
3. Point another at `@yourhandle`.

**Expect:**
- The first arrives on the phone.
- The second warns at load: a handle addresses a channel, not a private chat.

### F3 A restart does not skip or double-fire

**Steps:** with an `every: 10m` schedule, restart `serve` twice before it is due, then let it fire.

**Expect:**
- The next run is unchanged across both restarts.
- It fires exactly once: check the session for one message, not two.

### F4 Schedules through the API

**Steps:** `POST`, `PATCH`, `run` and `DELETE` on `/v1/agents/:id/schedules`.

**Expect:** each returns the documented shape. `run` fires now. A manifest-owned schedule refuses
`DELETE` with a hint.

## G. The 0.2.0 runtime API

Run these against the container (`docker compose up -d`), with `$TOKEN` set to
`DISPACH_API_TOKEN`.

### G1 ★ Templates

**Steps:**
1. Put a template under `/home/dispach/.dispach/templates/support/` (09-API-GUIDE §1b). A placeholder in a YAML file
   must be the whole value, unquoted (`name: {{vars.store}}`). A quoted or partial one is refused
   with `template_placeholder_placement`, which is itself a case to check.
2. `GET /v1/templates`.
3. `POST /v1/agents {"template":"support","name":"Acme","vars":{…}}`.

**Expect:**
- `201`, and the agent is adopted.
- A missing required var is refused, with a hint naming it.
- A value like `x", tools: {}` stays text in the written files.

### G2 ★ Secrets

**Steps:**
1. Create from a template without the key.
2. `GET …/secrets`.
3. `PUT …/secrets {"values":{"MODEL_API_KEY":"…"}}`.
4. `GET` again.
5. `PUT` a name the manifest does not read.

**Expect:**
- The agent is adopted on the `PUT`, and `set: true` appears.
- **No route ever returns the value.**
- The unknown name is refused.
- A variable also set in the server environment is listed under `shadowed`.

### G3 Usage and turns

**Steps:**
1. Two turns.
2. `GET /v1/usage?by=agent,model`.
3. `GET /v1/agents/:id/turns`.
4. The same calls with a key scoped to another agent.

**Expect:** the counts match the endpoint's billing. The scoped key sees nothing of this agent.

### G4 ★ Webhooks, verified with the official library

**Steps:**
1. Subscribe a receiver that verifies with the `standardwebhooks` npm package. A WS client sends
   `{type:"subscribe",agentId}` before `{type:"message",text}`.
2. Run a turn.
3. Stop the receiver (`docker stop`, so its name stops resolving) and run another turn.
4. `GET /v1/webhooks`.
5. Bring the receiver back.

**Expect:**
- Each delivery verifies.
- The failing hook shows `failing` and `lastError`.
- The retry arrives with the same `webhook-id`, including when the receiver's name did not resolve
  while it was down (`pending` stays above 0 until it is back).
- A private-network receiver is refused unless it is in `DISPACH_WEBHOOK_ALLOW`.
- `169.254.x` is refused even when it is listed.

### G5 Limits

**Steps:** set `maxConcurrentTurns: 1` and a small `tokens.max` by editing the agent's `agent.yaml`,
then `POST …/reload`. Limits are not settable over `PATCH /config`, by design. Start two turns at once, over HTTP,
over WS, from Telegram, and from a schedule.

**Expect:**
- HTTP answers `429 agent_at_capacity`, then `agent_token_budget_exhausted`, each with a hint.
- WS returns the same error frame.
- The Telegram sender gets a one-line reply.
- The schedule records the error.
- No turn is cut off mid-work.

### G6 `/v1/activity`, and the scope holes that are closed

**Steps:**
- `GET /v1/activity` with the server token, then with a scoped key.
- `POST /v1/agents/:id/stop` with a key scoped to another agent.

**Expect:** activity answers with the token and `403` with the scoped key. The stop answers `403`
when the key lacks `admin` (the capability is checked first, and a real and an imaginary agent answer
alike), and `404` with an `admin` key scoped to a different agent.

### G7 ★ A killed container serves again immediately

**Steps:** `docker kill <server>`, then `docker compose up -d`, and time `/v1/ready`.

**Expect:** ready in seconds (measured at about 1 s), not blocked by the dead pid-1 lease.

## H. Control plane

```bash
export DISPACH_CONTROL_TOKEN=$(openssl rand -base64 32)
export DISPACH_IMAGE=dispach:local            # or the pilot tag
export DISPACH_TEMPLATES=$PWD/qa-templates    # a host dir holding one template
export DISPACH_WEBHOOK_ALLOW=control DISPACH_SILO_ENV=DISPACH_WEBHOOK_ALLOW
export DISPACH_HOOK_URL=http://control:7600
docker compose -f packages/control/compose.yaml up -d --build
CP=http://127.0.0.1:7600
```

### H1 ★ Create, key, proxy

**Steps:**
1. `POST $CP/v1/silos {"subject":"qa_a"}`.
2. `POST …/silos/qa_a/keys`.
3. Through the proxy (`$CP/silos/qa_a/v1/…`): create an agent from the template, then send a
   streamed message.

**Expect:**
- The silo is ready in under a second: `201`, then `200` on a repeat.
- The key is shown once.
- The reply streams.

### H2 ★ Every cross-silo probe fails

**Steps:** create `qa_b` with its own key. With `qa_a`'s key, try:
- `qa_b`'s `/v1/agents`, `/v1/events` and `/v1/usage`;
- a message to `qa_b`'s agent;
- `qa_b`'s webhooks list.

Also try the operator token on `/silos/qa_a/v1/agents`.

**Expect:**
- Every one answers `401` or `404`, and none leaks data.
- The operator token is not a silo key, so it does not pass the proxy.
- **A single leak is Sev-1.**

### H3 The typed client through the proxy

**Steps:** a ten-line script using `dispach/client` with `baseUrl: "$CP/silos/qa_a"` and the silo
key: list agents, send, and stream.

**Expect:** the same results as H1.

### H4 `SILO_ENV`

**Steps:** add `MODEL_API_KEY` to `DISPACH_SILO_ENV`, pass it into the control container (see the
note below), then `recreate` `qa_a`.

**Expect:**
- The template agent runs with no key PUT.
- A name in `SILO_ENV` that is unset refuses the control plane's boot, naming it.

**Note:** `packages/control/compose.yaml` passes only the variables it names. A key reaches the
control process through a second compose file:

```yaml
# compose.local.yaml, beside it, never committed
services:
  control:
    environment:
      MODEL_API_KEY: ${MODEL_API_KEY:?}
```

Then `docker compose -f packages/control/compose.yaml -f compose.local.yaml up -d`.

### H5 Recreate, backup, restore, delete

**Steps:**
1. Run a turn in `qa_a`.
2. `GET …/backup > a.tgz`.
3. `POST …/recreate`.
4. `PUT` the backup into a new `qa_c`.
5. `DELETE qa_c`.

**Expect:**
- The history survives the recreate.
- `qa_c` holds `qa_a`'s agents and keys.
- `DELETE` removes the volume: `docker volume ls` no longer lists it.
- Each operation answers `409` while a turn is running.

### H6 Always on

**Steps:** leave `qa_a` idle for twice `IDLE_MS`, then check `docker ps`.

**Expect:** it is still running. `DISPACH_SUSPEND=on` is the only way it pauses.

### H7 ★ The monitor hears real turns

**Steps:** after a few turns, `GET $CP/v1/monitor` and `GET $CP/v1/monitor/failures`. Force a
`max_steps` turn.

**Expect:**
- The silo appears under `silos` and not under `unmonitored`.
- `firstTokenMs` p50 is filled in.
- The forced turn is listed in failures.
- With `ALERT_TG_*` set, an alert arrives once `minTurns` is reached and the rate crosses.
